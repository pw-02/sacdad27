\section{Discussion}
\label{sec:discussion}
\TITLE{} uses memory as the primary admission resource because memory capacity
determines whether proof stages can safely overlap on a node. Stage-aware
admission is not expected to improve every workload. Fine-grained partitioning
already reduces many jobs to modest memory footprints, so whole-job peak
reservation can permit substantial concurrency when the memory budget is
comfortable. \TITLE{} therefore activates stage-level accounting only when
peak-based admission would block a stage that still fits in the currently
available memory. The resulting benefit depends on how often such recoverable
memory slack occurs. Once memory pressure is relaxed, CPU contention can
instead become the limiting resource. The same framework could incorporate
CPU estimates when that contention dominates.

We treat partitioning and runtime scheduling separately. Partitioning defines
the proof jobs, while \TITLE{} controls their execution. The coordinator
provides request-level fairness rather than explicit deadlines or priorities,
which could be added as alternative scheduling objectives.

\section{Conclusion}
\TITLE{} treats partitioned zkML proof generation as a distributed serving
problem. It separates cluster-wide job placement from node-local admission,
uses historical resource profiles to protect memory, and reuses expensive
setup artifacts across requests. The key admission opportunity is not
concurrency by itself, but recoverable memory slack between a job's eventual
peak and the demand of its current stage. Guarded stage-aware admission leaves
whole-job behavior unchanged when that slack is not useful, while under a
48~GiB MobileNetV2 budget it reduces median request latency by 4.2--8.8\%
across bursts of 4--16 requests. Partitioned requests also scale effectively
across prover nodes, reaching 10.5--12.7\times speedup from one to ten nodes
across the three primary workloads.
