\section{Introduction}
\label{sec:intro}

Machine-learning inference is increasingly outsourced to remote services, as modern models often require more computation, memory, and specialized hardware than clients can practically provision locally~\cite{zhang2024hardware,sheng2023flexgen}. In this setting, the client observes the returned prediction but has no direct assurance that the specified model was evaluated correctly on the submitted input~\cite{kang2024scaling,qu2025zkgpt}. Re-executing the model locally would undermine the benefit of outsourcing, while inspecting the service's execution may require access to private inputs, model parameters, or intermediate values.

Zero-knowledge machine learning (zkML) addresses this problem by returning a cryptographic proof alongside the prediction~\cite{chen2024zkml,kang2024scaling,boyuan2021zen,chen2025zktorch}. The proof attests to correct execution without requiring the client to repeat the inference and can keep selected inputs or model values hidden. The resulting asymmetry is useful for verification but places most of the computational burden on the prover. zkML proof generation can be orders of magnitude slower than ordinary inference and consume large amounts of memory. For example, zkGPT~\cite{qu2025zkgpt} reports 147.7~s to prove the generation of 64 tokens compared with 94.55~ms for model execution, with peak prover memory reaching 240.5~GB.

Prior zkML work primarily reduces the cost of individual proofs through model transformations, optimized circuits, broader framework support, GPU acceleration, parallel proof accumulation, or partitioning~\cite{boyuan2021zen,chen2024zkml,ezkl,sin2024zkllm,chen2025zktorch,sanjaya2026zkcomposer}. These techniques improve how a model computation is represented and proved, and partitioning additionally exposes independently executable proof components. They do not, however, determine how proof work from multiple inference requests should share a finite prover pool. Once several requests are active, the runtime must choose among heterogeneous jobs from different requests, decide where those jobs execute, and control how much work each node admits at once.

This serving problem differs from simply maximizing parallelism within one inference. A request may expand into many proof jobs whose runtimes and memory demands differ by orders of magnitude. Memory demand also changes during proof construction, so a job's peak can substantially overstate the capacity it needs for much of its lifetime. At the same time, repeated executions of the same circuit can reuse expensive compiled circuits and proving keys. These properties couple scheduling decisions to both current resource pressure and the location of reusable artifacts.

Our characterization in Section~\ref{sec:characterization} shows why simple concurrency control is insufficient. Launching a fixed number of jobs says little about actual memory pressure, while reserving every job's peak demand for its full execution can leave capacity idle. A zkML serving runtime must therefore decide both \emph{where} proof jobs execute and \emph{when} resource-intensive stages may proceed.

\textbf{Our Work.}
We present \TITLE{}, a distributed runtime for concurrent zkML proof serving. \TITLE{} transforms each inference request into independently executable proof jobs and treats partitioning as the source of schedulable work rather than as the complete execution policy. A global coordinator assigns whole jobs across prover nodes using request-level fairness, historical job cost, node capacity, and setup locality. Each node then admits individual proving stages using recent stage-level memory profiles and current local capacity. This hierarchy keeps global placement simple while allowing fine-grained control over the resource that most directly limits local concurrency.

\TITLE{} also exploits repetition across inference requests. Compiled circuits and proving keys are persisted and cached on prover nodes so that recurring partitions can avoid repeated setup work. Setup locality influences placement only after request fairness and resource feasibility, preventing cache affinity from overriding memory safety. Jobs remain pinned to one node for an execution attempt, while lease-based retry and recovery handle failures without repeating already completed jobs from the same request.

We implement \TITLE{} around existing zkML backends, using EZKL~\cite{ezkl} as the primary backend and Halo2~\cite{halo2} as the underlying proof system. The proving protocol remains unchanged. We instrument the backend to expose execution stages and resource usage for characterization and admission decisions.
