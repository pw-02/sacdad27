\section{Introduction}
\label{sec:intro}

Machine-learning inference is increasingly outsourced to remote services, as modern models often require more computation, memory, and specialized hardware than clients can practically provision locally~\cite{zhang2024hardware,sheng2023flexgen}. In this setting, the client observes the returned prediction but has no direct assurance that the specified model was evaluated correctly on the submitted input~\cite{kang2024scaling,qu2025zkgpt}. Re-executing the model locally would undermine the benefit of outsourcing, while inspecting the service's execution may require access to private inputs, model parameters, or intermediate values.

Zero-knowledge machine learning (zkML) addresses this problem by returning a cryptographic proof alongside the prediction~\cite{chen2024zkml,kang2024scaling,boyuan2021zen,chen2025zktorch}. The proof attests to correct execution without requiring the client to repeat the inference and can keep selected inputs or model values hidden. The resulting asymmetry is useful for verification but places most of the computational burden on the prover. zkML proof generation can be orders of magnitude slower than ordinary inference and consume large amounts of memory. For example, zkGPT~\cite{qu2025zkgpt} reports 147.7~s to prove the generation of 64 tokens compared with 94.55~ms for model execution, with peak prover memory reaching 240.5~GB.

Prior zkML work primarily reduces the cost of individual proofs through model transformations, optimized circuits, broader framework support, GPU acceleration, parallel proof accumulation, or partitioning~\cite{boyuan2021zen,chen2024zkml,ezkl,sin2024zkllm,chen2025zktorch,sanjaya2026zkcomposer}. These techniques improve proving efficiency and expose parallelism within an inference, but leave a complementary systems problem when multiple inference requests share finite prover resources. Each request may expand into many heterogeneous proof jobs whose runtime and memory demand vary substantially, while repeated executions can reuse expensive circuit-specific artifacts.

Our characterization in Section~\ref{sec:characterization} shows that these properties make simple concurrency control inefficient. Launching too many jobs can oversubscribe memory, while reserving each job's peak demand for its full execution can leave capacity idle. A zkML serving runtime must therefore decide both where proof jobs execute and when resource-intensive stages may proceed.

\textbf{Our Work.}
We present \TITLE{}, a distributed runtime for concurrent zkML proof serving. \TITLE{} transforms each inference request into independently executable proof jobs and uses a hierarchical resource-management architecture that separates cluster-wide placement from node-local admission. The coordinator balances requests, runtime estimates, node capacity, and setup locality when assigning jobs. Each prover node then admits execution stages using recent stage-level memory profiles and current local capacity, allowing safe overlap without reserving a job's peak memory for its entire lifetime. Reusable compiled circuits and proving keys are cached and reused across requests when available.

We implement \TITLE{} around existing zkML backends, using EZKL~\cite{ezkl} as the primary backend and Halo2~\cite{halo2} as the underlying proof system. The proving protocol remains unchanged. We instrument the backend to expose execution stages and resource usage for characterization and admission decisions.
