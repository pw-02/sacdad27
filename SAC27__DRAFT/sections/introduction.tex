\section{Introduction}
\label{sec:intro}

Machine-learning inference is increasingly outsourced to remote services, as modern models often require more computation, memory, and specialized hardware than clients can practically provision locally~\cite{zhang2024hardware,sheng2023flexgen}. In this setting, the client observes the returned prediction but has no direct assurance that the specified model was evaluated correctly on the submitted input~\cite{kang2024scaling,qu2025zkgpt}. Re-executing the model locally would undermine the benefit of outsourcing, while inspecting the service's execution may require access to private inputs, model parameters, or intermediate values.

Zero-knowledge machine learning (zkML) addresses this problem by returning a cryptographic proof alongside the prediction~\cite{chen2024zkml,kang2024scaling,boyuan2021zen,chen2025zktorch}. The proof attests to correct execution without requiring the client to repeat the inference and can keep selected inputs or model values hidden. The resulting asymmetry is useful for verification but places most of the computational burden on the prover. zkML proof generation can be orders of magnitude slower than ordinary inference and consume large amounts of memory. For example, zkGPT~\cite{qu2025zkgpt} reports 147.7~s to prove the generation of 64 tokens compared with 94.55~ms for model execution, with peak prover memory reaching 240.5~GB.

Prior zkML work primarily reduces the cost of individual proofs through model transformations, optimized circuits, broader framework support, GPU acceleration, parallel proof accumulation, or partitioning~\cite{boyuan2021zen,chen2024zkml,ezkl,sin2024zkllm,chen2025zktorch,ivanov2025dsperse}. These techniques improve proving efficiency and expose parallelism within an inference, but leave a complementary systems problem once a partitioned request becomes a collection of heterogeneous proof jobs. Those jobs differ substantially in runtime and memory demand, compete for finite prover resources, and may reuse expensive circuit-specific artifacts across repeated executions.

Our characterization in Section~\ref{sec:characterization} shows why partitioning alone is not a complete execution policy. Fine-grained jobs reduce per-job memory and expose parallelism, but their resource demands remain highly uneven and change over the course of execution. A zkML runtime must therefore decide where jobs execute, how local memory is protected as stages progress, and when reusable setup artifacts should influence placement.

\textbf{Our Work.}
We present \TITLE{}, a distributed runtime for zkML proof serving. \TITLE{} operates on each partitioned inference request as a collection of independently executable proof jobs and uses a hierarchical resource-management architecture that separates cluster-wide placement from node-local admission. The coordinator balances requests, runtime estimates, node capacity, and setup locality when assigning jobs. Each prover node then admits execution stages using recent stage-level memory profiles and current local capacity. Reusable compiled circuits and proving keys are cached and reused across requests when available.

We implement \TITLE{} around EZKL~\cite{ezkl}, with Halo2~\cite{halo2} providing the underlying proof system. The proving protocol remains unchanged. We instrument the backend to expose execution stages and resource usage for characterization and admission decisions.

We evaluate \TITLE{} across convolutional and transformer workloads using characterization, resource-profile accuracy, setup reuse, and distributed scale-out experiments. Historical memory profiles have below 0.5\% median absolute error in all measured configurations, setup reuse removes 96.3--98.6\% of repeated setup time, and scaling a single partitioned request from one to ten prover nodes improves completion time by 10.5--12.7\times across the three primary workloads.

\textbf{Contributions.} This paper makes three contributions:
\begin{itemize}
    \item We characterize partitioned zkML inference as a serving workload, showing substantial variation across proof jobs, stage-dependent memory demand, predictable repeated executions, and opportunities for setup reuse.
    \item We design and implement \TITLE{}, which separates cluster-wide job placement from node-local stage admission and incorporates historical resource profiles and artifact locality.
    \item We evaluate the mechanisms that support this design, including profile accuracy and setup reuse, and demonstrate distributed scale-out across three model families with 10.5--12.7\times speedup from one to ten prover nodes.
\end{itemize}
