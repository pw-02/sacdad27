\section{Introduction}
\label{sec:intro}

Machine-learning inference is increasingly outsourced to remote services, as modern models often require more computation, memory, and specialized hardware than clients can practically provision locally~\cite{zhang2024hardware,sheng2023flexgen}. In this setting, the client observes the returned prediction but has no direct assurance that the specified model was evaluated correctly on the submitted input~\cite{kang2024scaling,qu2025zkgpt}. Re-executing the model locally would undermine the benefit of outsourcing, while inspecting the service's execution may require access to private inputs, model parameters, or intermediate values.

Zero-knowledge machine learning (zkML) addresses this problem by returning a cryptographic proof alongside the prediction~\cite{chen2024zkml,kang2024scaling,boyuan2021zen,chen2025zktorch}. The proof attests to correct execution without requiring the client to repeat the inference and can keep selected inputs or model values hidden. The resulting asymmetry is useful for verification but places most of the computational burden on the prover. zkML proof generation can be orders of magnitude slower than ordinary inference and consume large amounts of memory. For example, zkGPT~\cite{qu2025zkgpt} reports 147.7~s to prove the generation of 64 tokens compared with 94.55~ms for model execution, with peak prover memory reaching 240.5~GB.

Prior zkML work primarily reduces the cost of individual proofs through model transformations, optimized circuits, broader framework support, GPU acceleration, parallel proof accumulation, or partitioning~\cite{boyuan2021zen,chen2024zkml,ezkl,sin2024zkllm,chen2025zktorch,ivanov2025dsperse}. These techniques improve proving efficiency and expose parallelism within an inference, but leave a complementary systems problem when multiple inference requests share finite prover resources. Each request may expand into many heterogeneous proof jobs whose runtime and memory demand vary substantially, while repeated executions can reuse expensive circuit-specific artifacts.

Our characterization in Section~\ref{sec:characterization} shows that these properties make simple concurrency control inefficient. Reserving each job's peak demand for its full execution can leave capacity idle because memory demand changes substantially across proving stages. At the same time, fine-grained partitioning already reduces many jobs to modest memory footprints, so exposing more concurrency is not always useful. A zkML serving runtime must therefore identify when peak-based admission is actually restrictive rather than enabling stage-aware overlap unconditionally.

\textbf{Our Work.}
We present \TITLE{}, a distributed runtime for concurrent zkML proof serving. \TITLE{} operates on each partitioned inference request as a collection of independently executable proof jobs and uses a hierarchical resource-management architecture that separates cluster-wide placement from node-local admission. The coordinator balances requests, runtime estimates, node capacity, and setup locality when assigning jobs. Each prover node then uses a guarded stage-aware admission policy. Stage-level accounting is activated only when whole-job peak reservation would block a stage that can safely execute with the memory currently available. Otherwise the node retains whole-job admission, avoiding additional concurrency when there is little memory slack to recover. Reusable compiled circuits and proving keys are cached and reused across requests when available.

We implement \TITLE{} around EZKL~\cite{ezkl}, with Halo2~\cite{halo2} as the underlying proof system. The proving protocol remains unchanged. We instrument the backend to expose execution stages and resource usage for characterization and admission decisions.

We evaluate \TITLE{} across convolutional and transformer workloads, including concurrent execution and distributed scale-out. Under the default memory configuration, guarded admission avoids regressions by retaining whole-job admission when additional stage overlap is unnecessary and yields modest improvements for TinyBERT. Under a 48~GiB proving budget, where MobileNetV2 becomes memory constrained, stage-aware admission reduces median request latency by 4.2--8.8\% across bursts of 4--16 requests. Scaling a single partitioned request from one to ten prover nodes improves completion time by 10.5--12.7\times across the three primary workloads.

\textbf{Contributions.} This paper makes three contributions:
\begin{itemize}
    \item We characterize partitioned zkML inference as a serving workload, showing substantial variation across proof jobs, stage-dependent memory demand, predictable repeated executions, and opportunities for setup reuse.
    \item We design and implement \TITLE{}, which separates cluster-wide job placement from node-local admission and uses a guarded stage-aware policy to recover memory slack only when peak-based admission would otherwise block useful work.
    \item We evaluate \TITLE{} across multiple model families and deployment scales. Under memory-constrained MobileNetV2 serving, guarded stage-aware admission reduces median request latency by up to 8.8\%, while single-request scale-out reaches 10.5--12.7\times from one to ten prover nodes.
\end{itemize}
