\section{Evaluation}
\label{sec:evaluation}

We evaluate \TITLE{} by asking four questions: how effectively it serves
concurrent requests, how stage-aware admission compares with whole-job peak
reservation, whether historical stage profiles are accurate enough for
online admission, and how much setup reuse reduces repeated work. We also
measure single-request scale-out and sensitivity to partition granularity.

\subsection{Experimental Setup}
\label{sec:eval-setup}

\textbf{Platforms.}
Single-node experiments run on a dual-socket AMD EPYC 9354 server with
64 physical cores and 128~GiB of RAM. Multi-node experiments use up to
10 AWS m6a.4xlarge instances, each with 16 vCPUs and 64~GiB of RAM. One
prover node also hosts the coordinator, and Amazon S3 is used for artifact
transfer between the coordinator and prover nodes.

\textbf{Workloads.}
We evaluate TinyBERT, MobileNetV2, and NanoGPT (4L), summarized in
Table~\ref{tab:models}. Unless otherwise stated, we use one ONNX operator
per partition. Section~\ref{sec:eval-sensitivity} evaluates coarser
partitions.

\textbf{Policies.}
We compare three node-level execution policies while holding partitioning
and coordinator scheduling fixed. \emph{Fixed-$k$} limits each node to
\(k\) active proof jobs. \emph{Whole-job admission} reserves each job's
predicted peak memory until completion. \emph{\TITLE{}} instead reserves
the predicted memory of the stage about to run. Unless otherwise stated,
fixed concurrency uses \(k=8\).

\textbf{Profiles and traffic.}
Cold runs generate setup artifacts during execution, while warm runs reuse
artifacts generated beforehand. Historical profiles are collected in
separate runs under the same setup condition and initialized identically
across compared policies. Burst experiments submit
\(N\in\{1,4,8,16\}\) requests simultaneously and report request latency,
batch makespan, and peak memory.

\subsection{Single-Request Scale-Out}
\label{sec:eval-scale-out}

We next vary the prover pool from 1 to 10 nodes while holding the request
and partitioning fixed. Let \(T_p\) denote completion time with \(p\)
prover nodes and define speedup as \(T_1/T_p\).
Figure~\ref{fig:scale-out} reports completion time and speedup.

All three workloads benefit substantially from additional nodes. NanoGPT
(4L) decreases from 1108~s to 89~s, MobileNetV2 from 9639~s to 762~s,
and TinyBERT from 7900~s to 750~s, corresponding to \(12.4\times\),
\(12.7\times\), and \(10.5\times\) speedups. At 10 nodes, summed job
runtime per worker varies by only 116.8--118.2~s for NanoGPT and
557.1--560.1~s for MobileNetV2, indicating effective distribution of the
same proof workload across workers.

    \label{fig:scale-out}
\end{figure}

\textbf{Execution breakdown.}
Table~\ref{tab:scaleout-overhead} shows that proof generation dominates
compute time, while shared-storage cost is dominated by reads. Aggregate

\subsection{Resource Profile Accuracy}
\label{sec:profile-accuracy}

\TITLE{} estimates stage memory from recent executions of the same model
partition. We repeatedly execute representative partitions in isolation
and compare each observed peak with the estimate available beforehand.
With fewer than five prior measurements, \TITLE{} uses the largest
observed peak. Once five are available, it uses the empirical 90th
percentile of recent history.

Figure~\ref{fig:profile-accuracy} shows that median absolute prediction
error remains below 0.5\% in every measured configuration. Although
12.5--29.2\% of predictions underestimate the subsequent peak, the
largest observed shortfall is below 0.08~GiB. Thus, underprediction is
usually a small deviation around an otherwise stable memory profile.

\subsection{Setup Reuse and Partition Granularity}
\label{sec:eval-sensitivity}

\textbf{Setup reuse.}
Table~\ref{tab:setup-reuse} compares first-time generation with reuse from
the node-local cache. Reuse removes 96.3--98.6\% of aggregate setup time.
The corresponding proving keys occupy 59.1--287.5~GiB across the three
workloads, motivating a bounded cache rather than retaining every artifact
locally.

\textbf{Partition granularity.}
We vary the number of operators grouped into each proof job while holding
the model and backend fixed. Figure~\ref{fig:partition-granularity} shows
that coarser partitions increase aggregate prover time and peak job memory
while exposing fewer independently schedulable jobs. We therefore use one
operator per proof job in the main serving experiments.
