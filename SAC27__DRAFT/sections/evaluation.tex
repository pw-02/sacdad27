\section{Evaluation}
\label{sec:evaluation}

We evaluate \TITLE{} by asking three questions. How well does a partitioned request scale across additional prover nodes? Are historical stage profiles accurate enough to support node-local admission? How much setup reuse reduces repeated work, and how does partition granularity affect proving cost? Together, these experiments evaluate the execution mechanisms motivated by the characterization in Section~\ref{sec:characterization}.

\subsection{Experimental Setup}
\label{sec:eval-setup}

\textbf{Platforms.}
Single-node experiments run on a dual-socket AMD EPYC 9354 server with 64 physical cores and 128~GiB of RAM. Multi-node experiments use up to 10 AWS m6a.4xlarge instances, each with 16 vCPUs and 64~GiB of RAM. One prover node also hosts the coordinator, and Amazon S3 is used for artifact transfer between the coordinator and prover nodes.

\textbf{Workloads.}
We evaluate TinyBERT, MobileNetV2, and NanoGPT (4L), summarized in Table~\ref{tab:models}. These workloads span transformer and convolutional architectures and produce markedly different proof-job sizes and resource demands. Unless otherwise stated, we use one ONNX operator per partition. Section~\ref{sec:eval-sensitivity} evaluates coarser partitions.

\textbf{Profiles and setup conditions.}
Cold runs generate setup artifacts during execution, while warm runs reuse matching artifacts generated beforehand. Historical profiles are collected in separate runs under the same setup condition. The node-local controller uses the same estimator described in Section~\ref{sec:local-admission}, with predictions beginning after two prior observations.

\subsection{Single-Request Scale-Out}
\label{sec:eval-scale-out}

We first isolate the effect of adding prover nodes to a single inference request. For each workload, the request and partitioning remain fixed while the prover pool grows from 1 to 10 nodes. Let \(T_p\) denote completion time with \(p\) prover nodes and define speedup as \(T_1/T_p\). Figure~\ref{fig:scale-out} reports both completion time and speedup.

All three workloads benefit substantially from additional nodes. NanoGPT (4L) decreases from 1108~s to 89~s, MobileNetV2 from 9639~s to 762~s, and TinyBERT from 7900~s to 750~s, corresponding to \(12.4\times\), \(12.7\times\), and \(10.5\times\) speedups. These values are measured relative to the one-node distributed baseline.

The worker reports show that the scheduler distributes proving work evenly at larger scales. At 10 nodes, summed job runtime per worker varies by only 116.8--118.2~s for NanoGPT and 557.1--560.1~s for MobileNetV2. Aggregate proving work remains nearly unchanged as the node count grows, so the reduction in request time comes primarily from executing the existing job set in parallel rather than from doing less proving work.

\textbf{Execution breakdown.}
Table~\ref{tab:scaleout-overhead} separates proof execution from shared-storage transfer for all three workloads. Proof generation remains the dominant compute cost, while verification is small by comparison. Shared-storage traffic is read-heavy because prover nodes retrieve request and reusable artifacts, whereas generated outputs are comparatively small.

For MobileNetV2 and NanoGPT, aggregate S3 read time also remains broadly stable as the prover pool grows, ranging from 798--848~s and 247--274~s, respectively, across the 1--10 node runs. Thus, for these workloads, scaling a fixed request across more prover nodes does not substantially increase its total transfer work over the evaluated range. The aggregate times in Table~\ref{tab:scaleout-overhead} may overlap in wall-clock execution, so they explain where work is spent rather than summing directly to request latency.

\subsection{Resource Profile Accuracy}
\label{sec:profile-accuracy}

\TITLE{} estimates stage memory from recent executions of the same model partition. We therefore test whether repeated executions are stable enough for those histories to support online admission. The repeated-run microbenchmark uses the same three workloads as the main evaluation. It executes representative partitions in isolation and records the peak memory of the admission-relevant execution region. Cold runs include setup and proving, while warm runs measure proving after matching setup artifacts are already available.

For each execution, the prediction is constructed using only earlier observations from the same partition and setup condition. Starting with two prior observations, we use the maximum while fewer than five observations are available, and the empirical 90th percentile thereafter. Figure~\ref{fig:profile-accuracy} reports both the median absolute prediction error and how often the prediction falls below the subsequently observed peak.

Memory demand is highly repeatable in these measurements. Median absolute prediction error remains below 0.5\% in every measured configuration. Underprediction occurs in 12.5--29.2\% of cases, but its magnitude is small, with the largest observed shortfall below 0.08~GiB. These measurements show that recent executions provide sufficiently stable inputs for the admission controller, while the live-memory check in Section~\ref{sec:local-admission} provides a second guard against deviations.

\subsection{Setup Reuse and Partition Granularity}
\label{sec:eval-sensitivity}

\textbf{Setup reuse.}
Table~\ref{tab:setup-reuse} compares first-time generation with reuse from the node-local cache. Reuse removes 96.3--98.6\% of aggregate setup time across the three workloads. The largest absolute saving occurs for MobileNetV2, whose setup work falls from more than 14{,}600~s to 391~s when matching artifacts are already local.

The savings come with a substantial storage footprint. Proving keys occupy 68.8~GiB for TinyBERT, 287.5~GiB for MobileNetV2, and 59.1~GiB for NanoGPT. Reuse can therefore eliminate most repeated setup work, but retaining every artifact on every node is impractical. This tradeoff motivates the bounded cache and locality-aware placement described in Section~\ref{sec:setup-reuse}.

\textbf{Partition granularity.}
We vary the number of operators grouped into each proof job while holding the model and backend fixed. Figure~\ref{fig:partition-granularity} shows that coarser partitions increase aggregate prover time and peak job memory while exposing fewer independently schedulable jobs. The effect is especially pronounced for MobileNetV2, where larger groups quickly concentrate both proving work and memory into individual jobs.

We therefore use one operator per proof job in the main experiments. This choice is not intended as a claim that operator-level partitioning is universally optimal. Rather, among the configurations evaluated here it exposes the finest scheduling granularity while avoiding the additional proving cost and memory demand introduced by coarser grouping.
