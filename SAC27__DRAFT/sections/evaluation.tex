\section{Evaluation}
\label{sec:evaluation}

We evaluate \TITLE{} by asking four questions: how effectively it serves concurrent requests, how stage-aware admission compares with whole-job peak reservation, whether historical stage profiles are accurate enough for online admission, and how much setup reuse reduces repeated work. We additionally measure single-request scale-out and sensitivity to partition granularity.

\subsection{Experimental Setup}
\label{sec:eval-setup}

\textbf{Platforms.}
Single-node experiments run on a dual-socket AMD EPYC 9354 server with 64 physical cores and 128~GiB of RAM. Multi-node experiments use up to 10 AWS m6a.4xlarge instances, each with 16 vCPUs and 64~GiB of RAM. One prover node also hosts the coordinator, and Amazon S3 is used for artifact transfer between the coordinator and prover nodes.

\textbf{Workloads.}
We evaluate TinyBERT, MobileNetV2, and NanoGPT (4L), summarized in Table~\ref{tab:models}. These workloads span transformer and convolutional architectures and produce markedly different proof-job sizes and resource demands. Unless otherwise stated, we use one ONNX operator per partition. Section~\ref{sec:eval-sensitivity} evaluates coarser partitions.

\textbf{Admission policies.}
We compare two node-level admission policies while holding partitioning and coordinator scheduling fixed. \emph{Whole-job admission} reserves each job's predicted peak memory until completion. \emph{\TITLE{}} instead reserves the predicted memory of the stage about to run. Both policies use the same historical memory information, differing in the granularity at which it is reserved. This isolates the benefit of exploiting stage-varying memory demand from differences in prediction or placement.

\textbf{Profiles and traffic.}
Cold runs generate setup artifacts during execution, while warm runs reuse matching artifacts generated beforehand. Historical profiles are collected in separate runs under the same setup condition and initialized identically across compared policies, so evaluation runs do not bootstrap from outcomes observed earlier in the same comparison. Burst experiments submit concurrent requests and report request latency and batch makespan. Because fine-grained partitioning already makes many jobs small, we also evaluate MobileNetV2 under a controlled 48~GiB proving budget on the same 128~GiB host. The 48~GiB value is an admission budget rather than the machine's physical memory. It remains above MobileNetV2's largest observed job peak of 41.45~GiB, so every job is individually feasible while whole-job peak reservation has little room to overlap the largest jobs.

\subsection{Performance Under Concurrent Requests}
\label{sec:eval-serving}

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{figures/sacdad/eval/burst_serving.pdf}
\caption{MobileNetV2 burst serving under a 48~GiB proving budget. Bars compare whole-job peak reservation with \TITLE{}'s stage-aware admission for median request latency and batch makespan. Lower is better.}
\label{fig:burst-performance}
\end{figure}

As Figure~\ref{fig:partition-benefits} shows, partitioning already reduces the memory footprint of the work presented to the runtime. As a result, many proof jobs are small enough that whole-job peak reservation can still admit substantial parallelism when memory is plentiful. Stage-aware admission therefore does not necessarily improve performance in that regime. We evaluate it under controlled memory pressure, where reserving every job's peak for its full execution is more likely to delay stages whose current memory demand is much smaller.

Figure~\ref{fig:burst-performance} shows MobileNetV2 with the proving budget restricted to 48~GiB. For bursts of 2, 4, 8, and 16 requests, median request latency falls from 21{,}100.7~s to 20{,}088.4~s, from 42{,}057.1~s to 38{,}340.0~s, from 84{,}134.9~s to 78{,}689.0~s, and from 168{,}174.4~s to 161{,}068.5~s. These correspond to improvements of 4.8\%, 8.8\%, 6.5\%, and 4.2\%, respectively.

Batch makespan also improves for three of the four burst sizes. It falls from 21{,}130.8~s to 20{,}882.2~s at burst 2, from 42{,}078.3~s to 40{,}721.6~s at burst 4, and from 168{,}300.7~s to 161{,}074.9~s at burst 16, corresponding to improvements of 1.2\%, 3.2\%, and 4.3\%. At burst 8 the two policies are effectively unchanged, with makespans of 84{,}179.7~s and 84{,}246.2~s.

These results show that stage-aware admission is most useful when memory capacity is the binding resource. When partitioned jobs already fit comfortably within the available budget, whole-job reservation leaves little additional concurrency for stage-aware admission to expose. Under tighter memory pressure, stage-level admission can overlap low-memory work that whole-job reservation would otherwise delay.

\subsection{Single-Request Scale-Out}
\label{sec:eval-scale-out}

We next isolate the effect of adding prover nodes to a single inference request. For each workload, the request and partitioning remain fixed while the prover pool grows from 1 to 10 nodes. Let \(T_p\) denote completion time with \(p\) prover nodes and define speedup as \(T_1/T_p\). Figure~\ref{fig:scale-out} reports both completion time and speedup.

All three workloads benefit substantially from additional nodes. NanoGPT (4L) decreases from 1108~s to 89~s, MobileNetV2 from 9639~s to 762~s, and TinyBERT from 7900~s to 750~s, corresponding to \(12.4\times\), \(12.7\times\), and \(10.5\times\) speedups. These values are measured relative to the one-node distributed baseline.

The worker reports show that the scheduler distributes proving work evenly at larger scales. At 10 nodes, summed job runtime per worker varies by only 116.8--118.2~s for NanoGPT and 557.1--560.1~s for MobileNetV2. Aggregate proving work remains nearly unchanged as the node count grows, so the reduction in request time comes primarily from executing the existing job set in parallel rather than from doing less proving work.

\textbf{Execution breakdown.}
Table~\ref{tab:scaleout-overhead} separates proof execution from shared-storage transfer for all three workloads. Proof generation remains the dominant compute cost: mean aggregate proving time is 1{,}838.5~s for TinyBERT, 4{,}233.1~s for MobileNetV2, and 746.3~s for NanoGPT (4L), while verification contributes only 4.7~s, 31.8~s, and 7.1~s, respectively. Shared-storage cost is likewise dominated by reads. Mean aggregate S3 read time is 472.0~s for TinyBERT, 819.9~s for MobileNetV2, and 264.0~s for NanoGPT, compared with 21.7~s, 17.5~s, and 20.3~s of writes.

For MobileNetV2 and NanoGPT, aggregate S3 read time also remains broadly stable as the prover pool grows, ranging from 798--848~s and 247--274~s, respectively, across the 1--10 node runs. Thus, for these workloads, scaling a fixed request across more prover nodes does not substantially increase its total transfer work over the evaluated range. The aggregate times in Table~\ref{tab:scaleout-overhead} may overlap in wall-clock execution, so they explain where work is spent rather than summing directly to request latency.

\subsection{Resource Profile Accuracy}
\label{sec:profile-accuracy}

\TITLE{} estimates stage memory from recent executions of the same model partition. We therefore test whether repeated executions are stable enough for those histories to support online admission. The repeated-run microbenchmark uses the same three workloads as the main evaluation: TinyBERT, MobileNetV2, and NanoGPT (4L). It executes representative partitions in isolation and records the peak memory of the admission-relevant execution region. Cold runs include setup and proving, while warm runs measure proving after matching setup artifacts are already available.

For each execution, the prediction is constructed using only earlier observations from the same partition and setup condition. Starting with two prior observations, we use the maximum while fewer than five observations are available, and the empirical 90th percentile thereafter. Figure~\ref{fig:profile-accuracy} reports both the median absolute prediction error and how often the prediction falls below the subsequently observed peak.

Memory demand is highly repeatable in these measurements. Median absolute prediction error remains below 0.5\% in every measured configuration. Underprediction still occurs in 12.5--29.2\% of cases, but its magnitude is small: the largest observed shortfall is below 0.08~GiB. This distinction matters for admission because an estimator can occasionally fall below the next observation without missing required capacity by a large amount. The live-memory check in Section~\ref{sec:local-admission} provides a second guard against such deviations.

\subsection{Setup Reuse and Partition Granularity}
\label{sec:eval-sensitivity}

\textbf{Setup reuse.}
Table~\ref{tab:setup-reuse} compares first-time generation with reuse from the node-local cache. Reuse removes 96.3--98.6\% of aggregate setup time across the three workloads. The largest absolute saving occurs for MobileNetV2, whose setup work falls from more than 14{,}600~s to 391~s when matching artifacts are already local.

The savings come with a substantial storage footprint. Proving keys occupy 68.8~GiB for TinyBERT, 287.5~GiB for MobileNetV2, and 59.1~GiB for NanoGPT. Reuse can therefore eliminate most repeated setup work, but retaining every artifact on every node is impractical. This tradeoff motivates the bounded cache and locality-aware placement described in Section~\ref{sec:setup-reuse}.

\textbf{Partition granularity.}
We vary the number of operators grouped into each proof job while holding the model and backend fixed. Figure~\ref{fig:partition-granularity} shows that coarser partitions increase aggregate prover time and peak job memory while exposing fewer independently schedulable jobs. The effect is especially pronounced for MobileNetV2, where larger groups quickly concentrate both proving work and memory into individual jobs.

We therefore use one operator per proof job in the main serving experiments. This choice is not intended as a claim that operator-level partitioning is universally optimal. Rather, among the configurations evaluated here it exposes the finest scheduling granularity while avoiding the additional proving cost and memory demand introduced by coarser grouping.
